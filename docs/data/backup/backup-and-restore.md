# 数据库备份与恢复

## 备份方式

MySQL 8.4 的基础方案采用逻辑备份，使用兼容版本的 `mysqldump`；也可按实际数据库服务使用其经过验证的备份机制。具体脚本、存储位置和恢复命令尚未实现。

业务表采用 InnoDB 时可使用 `--single-transaction` 获取一致性逻辑备份，但备份期间不能并发执行结构变更；非事务表需单独设计一致性策略。结构升级前先停止应用和任务写入，并确认其他写入方受控。

按实际对象范围明确备份表、视图、触发器、存储过程与事件，验证备份权限、客户端兼容性、字符集和 GTID 相关选项。单库备份不等于账户和权限也已备份，恢复所需账户由受控配置单独管理。

备份输出写入独立存储，检查执行退出状态、文件完整性和校验值，记录时间、MySQL 版本、应用版本及迁移状态。实际隔离恢复演练才能确认可恢复性，文件非空不能替代恢复验证。

## 计划与存储

目标策略为每日备份和数据库结构变更前备份。每日备份至少保留最近 7 份，迁移前备份至少保留最近 3 次，并保留独立存储位置的副本。实际保留容量、远端存储和执行计划上线前确认。

数据库数据卷与备份存储分离。备份不放在 Jenkins 临时工作区，不打包进应用镜像，也不作为普通构建产物上传；访问权限、加密和保留规则按数据敏感程度配置。不能直接复制运行中的 MySQL 数据目录来替代有效备份。

## 恢复流程

1. 确定备份、对应应用与迁移版本、MySQL 兼容版本和预期恢复时间点。
2. 将站点置于维护状态，停止应用与任务写入，确认连接和其他写入方受控。
3. 保存故障库状态和诊断材料，不直接覆盖唯一现场。
4. 将备份导入隔离 MySQL 实例或独立空库，核对结构、数据、约束和迁移记录。
5. 用兼容应用执行验收，明确目标库切换或恢复方案以及后续写入影响。
6. 按已验证方案完成目标恢复，核对运行账户权限、连接配置与健康状态，再恢复任务。
7. 记录恢复范围、结果和备份时间点之后的数据影响。

恢复旧备份会丢失备份后的写入，不能作为无损回退承诺。若需要时间点恢复，应另行配置并演练 binlog 保留和恢复链路；当前不宣称已经具备该能力。

## 上线前验收

实际演练一次备份、独立存储副本获取、隔离库恢复与应用启动，测量备份和恢复耗时。尚未完成演练时明确标记待验证。
