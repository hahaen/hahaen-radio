# 正式数据库恢复操作材料

## 需求与实际变更

补齐管理员可按阶段执行的[正式恢复手册](../../data/backup/formal-recovery-runbook.md)：批准恢复点与数据影响、独立副本隔离验收、停用其他发布/调度、值守文件锁与数据库锁、维护停写、故障现场备份、原表单语句归档、原生批次导入、完整结构/业务校验及两种持久状态下的应用恢复。

现有restore-isolated仍拒绝正式库和已有库；recover不导入SQL或补跑迁移。没有新增生产覆盖命令、Schema、业务迁移或应用代码。手工归档与导入由取得对应授权的数据库管理员执行，不把文档当作正式写入授权，不删除故障库或修改迁移历史。资料包含值守会话失效、归档/导入失败、前向升级、识曲预算保留、调度恢复及证据清理的明确边界。

同步数据、部署、备份及运维导航，更新进度与验收矩阵；正式恢复仍记为待外部条件。公开文档不含实际实例、身份、配置值或原始SQL数据，私有演练程序和原始输出留在Git排除归档中。

## Review 与验证

本轮只Review新增手册、关联说明与状态记录；读取现有备份、维护锁、迁移/发布状态及日志探针作为命令依据。核对真实CLI参数、raw与Node环境文件不能用source加载、口令不进入argv、双锁交接、无attempt和有attempt的分支差异、迁移历史完整前缀及旧镜像限制。

手册明确区分管理员值守和自动执行器：手工会话没有自动失锁取消，其他主机必须保持停用；交接数据库锁存在间隔，文件锁持续持有，无法保证条件时不执行。Linux的fd3同进程exec交接仍待目标验证，不将其写为已通过。导入采用显式skip-force、skip-reconnect和binary-mode的原生批次，不假定SOURCE能够中止全部错误，也没有使用当前MySQL不支持的选项。

本机通过既有受控连接访问真实MySQL 8.0.46，仅新建两个随机ha_radio_test_前缀夹具库：创建InnoDB父子表、Unicode/转义数据和明确的测试迁移历史，经现有备份入口创建/verify，从手册原文提取SQL生成片段、替换为本轮唯一夹具库并实际生成单条RENAME归档原表，原生客户端导入至已空的原夹具库。验证两个库各自数据及外键引用，故意SQL错误后下一条建表没有执行，故意多表命名冲突后没有发生部分改名。最后实际删除两个本轮临时库及临时文件。结果见[结构化证据](results.json)。这不是完整项目Schema恢复或正式库演练。

最初迁移身份没有创建此次隔离库的权限，未创建库即拒绝；随后使用已有受控运维身份完成上述隔离范围，未修改原身份授权。演练未访问其他业务表，未对开发/正式库执行SQL，未关闭生产TLS检查；本机通道不能证明正式MySQL TLS通过。

手册的11段shell示例经bash -n语法检查；没有执行其中的正式操作。纯文档执行内容Review、链接/目录及差异检查，不把历史219项普通测试当作本轮重跑结果。未构建应用、执行Docker、触发Jenkins、上传镜像或上线。同步upstream无新提交，12份任务文档按字节与权限完整恢复；复审后重复11段shell语法和101份Markdown/622条本地链接检查，代码依据摘要未变。
