# 技术方案评估

日期：2026-10-16。状态：方案评估完成，建议待实施；不修改现有技术基线。

## 需求与范围

评估当前技术组合是否适合浏览器电台应用，识别实施前最值得优化的部分，并明确验证边界。

本次读取实际文件、技术基线、系统设计、前后端专题、数据库、测试和部署资料，并核对部分官方技术文档。仓库当前只有文档、说明文件和目录占位，没有应用源码、依赖清单、工作区配置、锁文件或部署实现。因此下文是选型和设计评估，不能视为代码审计、依赖组合验收或性能测试结果。

## 总体判断

现有主栈适合当前项目，无需更换主要框架。最需要优化的是实施顺序、业务数据设计和可测量的验收条件。

| 方案 | 判断与理由 |
| --- | --- |
| React、TypeScript、Vite | 适合以交互和媒体为主的浏览器应用；可分别构建界面与引擎 |
| Three.js 原生 API | 与点位、地理坐标和场景交互需求匹配；现有统一帧循环和资源所有权约定合理 |
| 独立音频引擎 | 播放生命周期独立于页面，显式状态机和旧请求失效机制值得保留 |
| Zustand 与 TanStack Query | 职责已明确划分；界面状态与后端缓存分开，避免数据维护两份 |
| Fastify、Zod、共享 contracts | 适合类型化 REST 服务；运行时校验与数据库实体隔离合理 |
| MySQL、mysql2、Drizzle | 可以承担电台目录与任务记录；连接预算和单一迁移入口明确，无需重新更换数据库 |
| pnpm 单仓库 | 两个应用与共享契约规模适中，当前无需额外构建编排平台 |
| Caddy、Compose、Jenkins 手动发布 | 与单机部署、自有构建设施相符；维护成本主要来自数据库、备份和发布实现 |
| 浏览器直连音源 | 避免本项目服务器承担持续音频流量；需要接受用户网络与音源能力差异 |

上述判断基于已有需求边界。是否需要可索引的电台详情页、账户同步或代理音源，仍需分别定义需求后评估，不能据此假定这些功能已经确定。

## 优先优化事项

### P0：先确定电台数据来源与模型

现有资料明确了外部适配层，但供应商、授权条件和业务模型仍未确定。这是首版的依赖输入。

- 明确数据来源、使用许可、更新频率、调用限制和来源不可用时的行为。
- 将电台与播放地址分开：电台有稳定 ID，多个播放源有独立身份及优先级，地址改变不应丢失收藏关联。
- 定义名称、国家、语言、标签、坐标的规范化规则；允许未知值，不用错误默认坐标代替缺失数据。
- 定义导入去重、增量更新、失效与恢复规则；不要因一次探测失败就永久删除电台。
- 区分目录有效性、服务端探测结果和用户端播放结果，健康记录包含观测时间与适用环境。

先以少量代表性数据完成导入、查询、选台和播放，再扩大数据量。涉及服务端探测时沿用现有 URL 访问、重定向、内网阻断与并发限制约定。

### P0：用真实播放链路验证音频方案

现有音频文档已经识别跨域、用户手势、移动端后台和旧回调问题，当前缺的是实测结果。

先建立媒体测试矩阵：普通音频流、原生 HLS、hls.js、重定向、HTTPS 异常、不允许跨域、连接慢、断流和快速切台。先用可控音源验证错误分支，再用真实音源验证外部兼容性。

hls.js 要求 HLS 资源具备允许 GET 的 CORS 响应；它不能解决任意音源的网络和跨域问题。Web Audio 的媒体源节点对不满足跨域读取条件的资源可能输出静音，因此基础播放与分析链路需要分别设计和验证。无法分析时允许继续基础播放，不能把模拟动画呈现为真实频谱。

验收记录应包括首播耗时、成功或失败分类、切台后是否仅当前音源继续播放、实际声音输出，以及 iOS Safari、Android 浏览器的锁屏、后台、系统中断与恢复结果。自动化 WebKit 不能代替这些设备验证。

### P1：明确首版依赖的启用时机

保留当前选型，但分阶段初始化实际需要的能力：

- 先完成工作区、React 页面、Fastify API、共享契约和最小数据库迁移。
- 再完成选台、播放、切台、错误反馈与本地收藏的完整链路。
- 接入图形场景，按需加载 Three.js 与 hls.js，避免阻塞基础界面。
- 出现较大缓存、可转移的重计算或确定的周期任务时，再启用 IndexedDB、Worker 和任务入口的相应实现。

暂不增加 Redis、消息队列、微服务、Kubernetes 或额外 monorepo 编排工具。是否启用额外服务应由多实例协调、实际查询压力或可靠任务需求驱动。Jenkins 可以分阶段落地，首版仍需具备必要检查与手动发布能力。

### P1：补齐图形数据接口与性能预算

现有渲染约定覆盖批量绘制、DPR 和资源清理，但尚无实际数据规模、接口形态或设备基线。

建议将地图点位、搜索结果和电台详情分开设计：点位响应只传渲染与选择必需字段，详情按选择加载；根据实测结果选择压缩快照、区域查询或其他数据策略，不对未测量的数据量直接承诺全量传输或复杂空间索引。

为代表性数据集记录压缩响应大小、解析与场景准备耗时、绘制调用、帧时间、长任务和内存趋势。桌面 60fps、移动端 30fps 可以作为首轮候选目标，需同时固定设备、浏览器、数据量和交互场景；这些数值不是已达到的结果。

明确 WebGL 2 不可用时的 DOM 列表与播放器路径；处理上下文丢失、容器变化和重复进入页面。空闲时按需渲染，动态效果活跃时维持帧循环；页面隐藏时降低图形负载，音频生命周期单独管理。

### P1：优先验证依赖集成薄弱点

版本组合的元数据核对不能替代实际安装与构建。初始化阶段优先完成以下冒烟验证：

1. 固定 Node.js、pnpm、直接依赖和单一锁文件，全新环境可复现安装。
2. 共享 contracts 同时被 Vite 与编译后的 Node.js ESM 正确导入。
3. Fastify 与 Zod 适配器完成查询参数解析、非法请求处理、响应校验和 OpenAPI 输出；请求错误与内部响应错误分类正确。
4. Drizzle Schema、Kit、mysql2 与 MySQL 8.4 完成空库迁移、旧结构升级和数据保留验证。
5. 前后端生产产物及镜像能够启动，环境配置被明确加载、校验且不进入前端产物。

适配器应按安装时的维护状态和版本要求选择。核对时 Fastify 官方文档列出 `@fastify/type-provider-zod`，其仓库对 Zod 有具体最低版本约束，因此只写“Zod 4”不足以确定最终兼容组合。本次未安装或锁定任何候选版本。

### P2：把缓存、发布和运维约定落实为可观察结果

- 公共目录接口按数据更新方式选择 ETag、缓存有效期和失效机制；数据库已有索引与缓存响应不足时再评估额外缓存服务。
- 在测试发布中保留一个旧页面会话，更新 Web 后再触发懒加载，确认旧哈希资源不会立即失效；明确旧资源保留或可恢复刷新策略。
- 在已有日志和健康检查方案上补充最小指标：API 延迟和错误率、连接池等待、目录新鲜度、任务失败、磁盘与备份状态。
- 单独记录客户端播放失败分类与首播耗时；不要收集完整音源 URL 中的访问参数或不必要的用户信息。
- 明确任务在服务停机期间错过调度后的补跑或跳过策略，不能仅以 cron 表达式表示执行保证。
- 上线前按已有方案完成隔离恢复演练，测量实际恢复耗时，再确定可接受的数据恢复点与恢复时间。

上述是对已有设计的细化建议，不表示当前缺少的能力均需在首版一次性实现。

## 推荐实施顺序

1. 确定首版功能边界、数据来源和代表性音源，建立可运行工作区。
2. 完成数据库、API、选台与基础播放器的完整链路，验证真实设备播放。
3. 接入图形场景、轻量点位契约和设备降级，测量真实数据下的性能。
4. 完成本地偏好、国际化及首版实际需要的搜索等交互。
5. 完成容器、迁移入口、手动发布、备份恢复和上线验收。
