# 数据库备份与恢复

## 备份方式

使用 SQLite 在线备份机制，通过 better-sqlite3 的备份接口或经过验证的 SQLite 备份工具生成一致性快照。运行中的 WAL 数据库不能只复制主数据库文件作为完整备份。

备份输出写入独立目录，完成后进行完整性检查并记录校验值、时间、应用版本和迁移版本。只有校验成功的快照才标记为可恢复备份。

## 计划与存储

目标策略为每日备份和数据库结构变更前备份。每日备份至少保留最近 7 份，迁移前备份至少保留最近 3 次，并保留独立存储位置的副本。实际保留容量、远端存储和执行计划上线前确认。

数据库目录与备份目录分离。备份不放在 Jenkins 临时工作区，不打包进应用镜像；访问权限和保留规则按数据敏感程度配置。

## 恢复流程

1. 确定要恢复的快照、对应应用版本和预期数据时间点。
2. 将站点置于维护状态，停止 API 与任务进程，确保连接关闭。
3. 保存故障现场及数据库相关文件，防止覆盖排查材料。
4. 在隔离目录验证快照完整性和兼容应用的启动。
5. 由已验证的恢复脚本处理目标数据库及旧 WAL/SHM 文件，避免新旧文件混用。
6. 恢复文件权限，启动兼容版本，检查数据和健康状态。
7. 记录恢复范围、结果和快照之后的数据影响。

恢复旧快照会丢失快照后的写入，不能作为无损回退承诺。生产恢复需明确采用的数据时间点。

## 上线前验收

实际演练一次备份、异地副本获取、隔离恢复与应用启动，测量备份和恢复耗时。尚未完成演练时明确标记待验证。
