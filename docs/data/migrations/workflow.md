# 数据库迁移流程

状态：迁移机制已选定，当前没有已准备或已执行的业务迁移。

## 开发阶段

1. 修改 Drizzle Schema。
2. 使用固定版本的 Drizzle Kit 生成迁移 SQL 与元数据。
3. 审核 SQL 的建表、重建表、数据转换、索引与约束影响。
4. 在空数据库验证完整初始化。
5. 在含代表性旧结构与数据的临时数据库验证升级和数据保留。
6. 将 Schema、SQL、元数据和必要的数据转换脚本一起版本化。

迁移一旦在共享环境执行，就不直接修改已有文件；后续修正使用新迁移。生产不使用绕过版本记录的直接 Schema 推送。

## 生产执行

迁移由 Jenkins 发布中的独立阶段调用，同一环境禁止并发发布。API 与任务不会在启动时争抢执行迁移。

涉及结构变更时，先准备维护窗口、停止写入进程、生成并校验备份，再运行一次迁移入口。SQLite 迁移可能重建表，应评估额外磁盘空间与实际耗时。

执行完成后记录目标环境、发布标识、迁移清单和结果，再启动应用并验证。失败时停止后续发布，不假定所有迁移都自动回滚。

## 状态表述

发布记录必须区分：

- 已生成 SQL，尚未执行。
- 已在临时数据库验证。
- 已在指定目标环境执行。
- 已完成应用与数据验收。

脚本名称、正式命令与首次迁移清单在实现后补充；本文件中的流程不代表命令已经存在。

恢复原则见[备份与恢复](../backup/backup-and-restore.md)，执行顺序见[发布与回退](../../deployment/releases/release-and-rollback.md)。
